# 同类开源项目怎么把米家摄像头画面播出来

研究时间：2026-11-16。样本已克隆到工作区 `_camera_ref/`（共 28MB，均为 `--depth 1`），
下文所有结论都能在这些目录里逐行核对。

## 一、结论先行

能在浏览器里出画面的实现，**没有一个**用 MIoT 的 `start-p2p-stream`
（我们 `routes/camera.py` 调的那个接口，实机回 `-704000000 / http 500`）。
它们只有三条路：

| 路线 | 代表 | 云端参与的部分 | 媒体通路 |
|---|---|---|---|
| A 本地 P2P 直连 | go2rtc 的 `xiaomi://` 源 | 只取令牌/密钥（`miss_get_vendor`、`devicepass`） | UDP 直连摄像头 |
| B 官方原生库 | Miloco / ha-xiaomi-miot-camera | OAuth2 取 access_token | 小米 PPCS（P2P + 中继） |
| C 局域网 RTSP | mijia_camera 的本地模式 | 只读设备表拿 `local_ip` | `rtsp://ip:554/ch0_0.h264` |

三条路都要求**这台电脑能向摄像头发 UDP/TCP 包**。没有一个项目是纯云端 HTTP 拉流。

## 二、逐个拆

### 1. AlexxIT/go2rtc（1.9.13 起原生支持小米）

- `internal/xiaomi/xiaomi.go`：用账号 `passToken` 走云接口
  `/v2/device/miss_get_vendor` 拿 vendor（`tutk` / `cs2`）、设备公钥、签名，
  失败再回退 `/device/devicepass`（legacy）。
- `pkg/xiaomi/miss/client.go`：按 vendor 分派，`tutk` → `pkg/tutk`，`cs2` → `miss/cs2`。
- `pkg/tutk/conn.go`：目标端口等于 `10001` 走 `connectRemote`（TUTK 主服务器中转），
  否则 `connectDirect`（本地直连）；握手硬超时 **5 秒**。
- **README 原话**：`Connection to the camera is local only.`

这是最关键的一条证据：go2rtc 的小米源是**本地直连**设计。远程/跨网段它不负责。

我们此前用它试过：`miss_get_vendor` 成功（拿到 `vendor=tutk`、`uid`、
`device_public`、`sign`），说明云端那一半是通的；卡在 P2P 那一半。

### 2. XiaoMi/xiaomi-miloco（官方，3.5k star）

- `backend/miot/src/miot/camera.py`（1374 行，ctypes 封装）
- 原生库四份：`libs/{darwin,linux}/{arm64,x86_64}/libmiot_camera_lite.{dylib,so}`
  —— **macOS 有库**，本机 x86_64 可直接加载。
- 能力：原始 H264/H265 帧回调、JPG 解码、PCM、多通道、多档画质。
- 入口：`miot_camera_init(access_token, cloud_server)`，token 走小米
  OAuth2 授权码（`client_id=2882303761520431603`，`account.xiaomi.com/oauth2/authorize`）。
- 官方文档 `knowledge/03-features/live-camera-view.md` 明确写着：
  「实时观看依赖摄像头与 Miloco 服务在**同一局域网**；PPCS P2P 连接需要 UDP 入站」
  「**不支持跨局域网/公网访问**，需摄像头和服务在同一网络」
- 前端实现值得照抄：WS 推 H264 NAL，secure context 用 WebCodecs，
  非 secure 回退 `vendor/jmuxer.min.js`（Annex-B → fMP4 → MSE）。

### 3. miiot/micam（910 star）

纯桥接：登录 Miloco → `wss://.../api/miot/ws/video_stream?camera_id=&channel=`
收裸流 → 管道喂 ffmpeg → 推 RTSP。

两个工程细节值得记：

- `waiting_for_keyframe`：收到第一个 IDR（H264 NAL 5 / HEVC NAL 16~20）之前，
  收到的包全部丢弃。不这么做 ffmpeg 会花屏或一直等不到 SPS/PPS。
- ffmpeg 参数：`-use_wallclock_as_timestamps 1 -analyzeduration 20M -probesize 20M -f hevc -i pipe:0 -c copy`。

### 4. Ricky-Hao/ha-xiaomi-miot-camera

自带官方 `libmiot_camera_lite.so`（linux arm64/x86_64）+ mediamtx，
把帧推到 `rtsp://127.0.0.1:8554/camera/<did>/<channel>`，HA 侧再走 WebRTC。
本质是同一条 B 路线，只是把「官方库」换了个包装。

### 5. DHJ999/mi-home（米家看家）

唯一自称**跨网络**可看：`go2rtc-cs2.exe`（Release 里单独发，19.9MB，改过的
go2rtc，**闭源**）走「云端 P2P 中继」，配套 Node + ffmpeg + WebRTC。

- 只对 `isa.camera.hlc7` / `isa.camera.hlmax`（新机型、cs2 协议）实测过。
- 我们的机型是 `chuangmi.camera.v2`，云端给的 vendor 是 `tutk`，
  走不到它那条 cs2 中继上；而且产物是 Windows exe，本机跑不了。
- 但它的工程经验可用：
  1. 关播放器必须显式 `DELETE /api/streams?src=`，否则小米 P2P 会话不释放，
     拖几次进度条新连接就起不来；
  2. 建流时就定画质档位（`subtype=`），运行中切档位有兼容问题；
  3. 转码链 `ffmpeg:rtsp://127.0.0.1:8554/<name>#video=h264#audio=opus#timeout=30`。

### 6. halongsx/mijia_camera

两条腿：本地 RTSP（米家 App 里开「局域网查看」，地址形如
`rtsp://user:pass@<local_ip>:554/ch0_0.h264`），或把 go2rtc / MediaMTX 当中继。
本地模式是最省事的一种，但前提仍然是**同网可达**。

## 三、我们的现状对照

| 环节 | 同类项目 | 我们 |
|---|---|---|
| 取流入口 | `miss_get_vendor` / `devicepass` / 官方库 / 本地 RTSP | `start-p2p-stream`（云回 -704000000） |
| P2P 客户端 | go2rtc 的 tutk/cs2 实现，或官方 PPCS 库 | 无 |
| 转码 | ffmpeg（hevc→h264） | 无 |
| 分片/封装 | HLS 切片 或 fMP4+jmuxer | 无 |
| 前端播放 | hls.js / jmuxer / WebCodecs | 只有失败提示 |

也就是说：UI 那层已经够用，缺的是取流链路的三层（P2P、转码、封装），
而这三层在任何项目里都默认「网络是通的」。

实测本机网络：

```
本机       192.168.1.198/24   默认网关 192.168.1.1
摄像头     192.168.31.56      ping 2 发 2 丢；TCP 32761/10001/554 全部超时
小米路由   192.168.1.225      ping 通（11ms），32761/10001/554 全部 connection refused
```

摄像头在小米路由的 LAN 侧，路由在上一级网络里只做 NAT 出站、不做入站转发 ——
双重 NAT。所以任何 P2P 直连（A/C 路线）在本机都必然失败，
官方 PPCS（B 路线）按官方文档也要求同网 UDP 入站。

## 四、可选的三条落地路径

1. **先确认有没有本地 RTSP**（最省事）
   米家 App → 摄像头 → 设置，找「局域网查看 / LAN」。有的话地址就是
   `rtsp://<user>:<pass>@<ip>:554/ch0_0.h264`，我们只要加一层 HLS 切片就能播。
   代价最小，但仍然要先解决可达性。

2. **组网 + go2rtc**（通用）
   摄像头那一侧任一台常开设备跑 Tailscale 子网路由（宣告 `192.168.31.0/24`），
   或者干脆在那侧跑 go2rtc。本机用 `xiaomi://` 源拉流，再切片成 HLS。
   免费、不绑卡，但需要那侧有设备。

3. **官方 dylib 直接嵌进 Flask**（体验最好）
   `libmiot_camera_lite.dylib` + ctypes，拿原始 H264 帧，服务端只做 fMP4 封装
   （或直接透传），浏览器用 jmuxer 播。不需要 go2rtc、不需要 ffmpeg，内存最省。
   代价：要走一遍小米 OAuth2 授权，且同样要求同网。

## 五、无论走哪条都该先改的两处

1. `routes/camera.py` 的取流入口用错了接口 —— `start-p2p-stream` 这条云接口
   对这类机型不回可用地址。应改成 `miss_get_vendor` / `devicepass` 拿 P2P 令牌，
   或直接接官方库。
2. `services/scheduler.failure_hint_for` 里 `"-7" in text` 会把 `-704000000`
   这类云错误码误判成「设备离线」，导致提示文案完全指错方向。

## 七、实测：这台机型的「非局域网取流」为什么走不通

现场条件：摄像头 `chuangmi.camera.v2`（did 79600034，2017 年 TUTK 固件），
PC 在 `192.168.1.198`，摄像头在 `192.168.31.56`（小米路由二级 NAT 后面）。

### 7.1 官方库路线：库本身不支持这台机型

跑通了与官方客户端完全相同的 OAuth2 授权（`client_id=2882303761520431603`，
回调 `mico.api.mijia.tech/login_redirect`，无 client_secret），换到 access_token
（195 字符，有效期 3 天）。`libmiot_camera_lite.dylib v0.1.7` 加载正常、
`miot_camera_init` 返回 0，但一启动就退出：

```
[status] 2 CONNECTING
[lib] Can't support TUTK vendor.
[lib] miss_client_vendor:1108 ...
[status] 1 DISCONNECTED @0.3s
```

`strings` 该库可见 `Can't support TUTK vendor.` / `Can't support AGORA vendor.`
以及整套 `CS2 PPCS_*` 符号 —— 即 PC 版只编译了 CS2（MISS 新固件）通道，
TUTK 老固件通道被裁掉了。`camera_extra_info.yaml` 里也没有 `chuangmi.camera.v2`。

### 7.2 TUTK 主服务器路线：六台全部静默

用 go2rtc 的包格式（`ConnectByUID(stageGetRemoteIP)`，112 字节 magic
`04 02 19`，uid `52K3F4LPEMZRR3LT111A`）直接打六台 master：

| 主服务器 | IP | 结果 |
|---|---|---|
| m1.iotcplatform.com | 50.19.254.134 | 静默 6s |
| m2.iotcplatform.com | 15.164.195.115 | 静默 6s |
| m3.iotcplatform.com | 50.7.132.58 | 静默 6s |
| m4.iotcplatform.com | 120.79.183.253（阿里云杭州） | 静默 6s |
| m5.iotcplatform.com | 23.237.32.106 | 静默 6s |
| m6.iotcplatform.com | 139.162.174.232 | 静默 6s |

已排除沙箱干扰（关沙箱复测同样静默）、已排除只发 RemoteIP 的协议顺序问题
（先 GetPublicIP 再 GetRemoteIP 也静默）。go2rtc 自身的 5s deadline 拨号
（m1~m6 逐个跑）也全部 `i/o timeout`。

顺带记录一个排查坑：本机 TCP `connect` 会被拦截层伪造成「立即成功」，
连 `1.2.3.4:10001`、`203.0.113.7:9999` 都返回 0.00s 成功 ——
所以「TCP 通」在这台机器上不能作为可达性证据，只有收到真实回包才算。

### 7.3 MIoT 路线：云接口直接拒绝

spec 里 `p2p-stream` 服务只有两个动作，且 `in: []`、`out: []`：

```
start-p2p-stream  00002839   Start P2P Stream（无入参、无出参）
stop-stream       00002822   Stop Camera Stream
```

调用 `start-p2p-stream` 回 `-704000000 / http 500`（0.0s 立即拒绝），
而同设备 `stop-stream` 正常返回 —— 排除权限与通道问题。该机型 spec 里
也没有任何 snapshot / 云录像类能力可替代。

### 7.4 官方口径

小米 IoT 开发者文档（`iot.mi.com` → 扩展开发 → P2P 点对点传输）写明：
P2P 能力通过「米家扩展程序 SDK」提供，只能在米家 App 内使用，
且 TUTK 固件需要 `setCurrentDeviceIsMissFirmware(false)` 上报；
iOS/Android 两端都支持 TUTK 与 MISS，但**没有 PC/服务端形态**。

### 7.5 结论

这台 2017 年的 TUTK 固件机型，P2P 取流只在米家 App 里可用。
PC 端四条路（官方 PC 库 / TUTK 主服务器 / MIoT 云接口 / 局域网直连）
分别卡在「库不支持」「主服务器不应答」「云接口拒绝」「跨 NAT 不可达」。

真正零成本的破局点不在代码侧，而在那一层 NAT：把小米路由从「二级路由」
改成「有线中继 / AP 模式」，摄像头就会拿到 `192.168.1.x` 的地址，
与 PC 同网段，四条路里除云接口外全部立即复活（局域网直连、
官方库、go2rtc 均可）。改动只需在小米路由 App 里切一次工作模式，
不需要在摄像头侧装任何软件、不需要公网 IP、不花钱。

替代做法（不想动工作模式时）：在小米路由后台给 `192.168.31.56` 配 DMZ
或把 32761/10001 做 UDP 端口映射，PC 侧用 `192.168.1.225` 作为摄像头地址
访问。代价是 TUTK 局域网协商会走随机端口，单端口映射不一定够，稳定性低于 AP 模式。

## 八、落地：先判「能不能播」，再决定播不播

这个客户端要给不同的人用，每家的摄像头固件不一样。与其让用户反复点
「获取实时画面」看一个必然失败的云错误码，不如在面板打开时就把结论说清楚。

### 8.1 判定链（每一条都有可复核的证据）

`services/camera_cap.py` 按顺序看四件事，任何一步能定性就停：

| 步 | 看什么 | 结论 |
|---|---|---|
| 1 | 设备 spec 里有没有 `p2p-stream` 服务 | 没有 → `unsupported`（门铃/猫眼部分型号） |
| 2 | 设备视图里的 `online` | 明确 `false` → `offline` |
| 3 | `localip` 与本机出口地址是否同 /24 | 决定「同局域网」这个条件满足与否 |
| 4 | 云端 `miss_get_vendor` 的 vendor | `cs2`/`mtp` → `wan`；`tutk`/`agora` → 只能局域网 |

同网段时再补一步实测：向设备 `32761/udp` 发 TUTK 局域网广播包
（68 字节、magic `04 02 19`、cmd `01 06 21`、UID 落在偏移 16），
有回包才认为局域网直连真能用。这比单看网段可靠 —— 路由器开了
AP 隔离时，同网段也照样不通。

设备 `localip` / `p2p_id` 取自云端 `/home/device_list` 的原始返回
（`device_list("full")`，字段 `localip`、`p2p_id`），不需要额外请求。

### 8.2 四种结论对应四种界面

| mode | 标题 | 占位文案 | 取流按钮 |
|---|---|---|---|
| `wan` | 可跨网络播放 | 实时画面需从设备取流 | 可点 |
| `lan` | 需同局域网 | 实时画面需从设备取流 | 可点（局域网直连真能出画面） |
| `lan_only` | 仅支持局域网 | 需在同一局域网内才能播放 | 置灰 |
| `unsupported` | 不支持取流 | 该设备不支持在 PC 端取流 | 置灰 |
| `offline` | 设备离线 | 设备离线，无法取流 | 置灰 |
| `unknown` | 需要先检测 | 实时画面需从设备取流 | 可点 |

`lan_only` / `unsupported` / `offline` 三种在 `/api/camera/stream` 入口就短路，
不再调用云端取流动作 —— 少一次必然失败的请求，也少一条误导性的错误码。

### 8.3 缓存

判定按 did 缓存 10 分钟（探测要打云端 + 发 UDP，不能每次开面板都跑一遍）；
vendor 单独缓存 6 小时（厂商不会变，避免反复撞 -127 风控）。
面板上的「重新检测」带 `force=1`，清掉该设备的缓存重新探测。

### 8.4 实测（本机 + 这台摄像头）

```
mode            lan_only
vendor          tutk（code 1，master_region CN，miss_version 3.1.9.0）
localip         192.168.31.56
pc_ip           192.168.1.198
same_lan        false
remote_playable false
```

### 8.5 交互后置：点了才判，播不了才弹窗

8.1 的判定链没变，但触发时机从「面板打开」改成「点了获取实时画面」。

原来面板一打开就摆一条状态条 + 一段说明，等于把「这台播不了」写在抽屉最显眼
的位置。可大多数时候用户根本不看实时画面，那条横幅只是在替少数场景占版面。
现在的分工是：

| 时机 | 发生什么 |
|---|---|
| 打开面板 | 不做任何检测，占位只有一句「实时画面需从设备取流」 |
| 点「获取实时画面」 | 后端先判定；`wan`/`lan` 继续取流，其余直接回 `capability` |
| 播不了 | 弹窗：结论 + 原因 + 要满足的条件 + 原始返回；底部「我已连到同一网络 / 重新检测」 |
| 关掉弹窗 | 占位文案换成对应结论（如「需在同一局域网内才能播放」），不再复述 |

实现要点：

- 判定不再单独发一次请求。`/api/camera/stream` 本来就在取流前做判定，这次把
  `capability` 一并回给前端，一次往返同时完成「判 + 取」。
- 弹窗挂在 `.drawer-layer` 上，不在详情弹框内部：`.sheet` 带
  `backdrop-filter`，会为 `position: fixed` 的后代建立包含块，弹窗会被裁在
  弹框宽度里。
- 弹窗关闭时保留最后一帧内容（组件内 `cache`），否则离场动画期间文案会被
  清空闪一下。
- 判定结论仍按 did 缓存 10 分钟；弹窗里的「我已连到同一网络」带 `force=1`
  强制重测，重测后若变成可播，直接接着取流，不用再点一次。

### 8.6 详情从右侧抽屉改为居中双列弹框

设备 / 自动化 / 天气三处详情统一换成居中弹框，参数一致：`min(920px, 100%)` 宽、
`min(86vh, 900px)` 高、圆角 `--r-lg`、头部固定、内容区自己滚动，760px 以下收成一列。

| 详情 | 左列 | 右列 |
|---|---|---|
| 设备 | 状态 → 控制 → 摄像头 | 历史趋势 → 显示名称 → 定时 → 自定义分组 |
| 自动化 | 只读的触发 / 动作明细 | 写入（改名、启停）→ 删除 |
| 天气 | 当前读数 → 城市与尺寸设置 | 24 小时温度曲线与逐时采样 |

两列各自 `flex-direction: column`，不是 grid 行对齐：设备详情的「控制」高度随控件数量
变化，一旦按行对齐就会在另一列留出大片空白。

设备详情的两条渲染条件：

- **控制**：`在线 && (开关数 > 0 || 可写控件数 > 0)`。离线设备的控制项本来就点不动，
  以前留一句「设备离线，控制项已隐藏」占着半列版面，现在整块不放。
- **历史趋势**：区分「还没拉到」与「确实没采样」。`store.historyReady[did]` 由
  `loadDrawerHistory` 无论成功失败都置位，打开弹框时先清掉该 did 的标记；只有
  取样回来且曲线非空才渲染，避免每次打开先闪一下再出现，也避免没数据时留一句
  「暂无历史数据」。

入场动效跟着改：原来是 x 轴 40px 滑入（右侧抽屉的方向感），居中弹框没有方向，
改成 y 轴 12px 抬升 + 0.985 缩放，0.32s `power3.out`；离场 0.18s 反向。函数名
`drawerEnter/drawerLeave` 保留，选择器换成 `.sheet`。

顺带修掉一个入口问题：天气卡原本按 `store.filter === 'all'` 显示，而 `validFilter`
会把这个值校准成「当前家庭」，于是这张卡与天气详情在选了家庭之后永远出不来。改成
认 `parseKey(filter).type` 为 `all` 或 `home`——天气是全局信息，家庭这一层显示，
进到具体房间或分组就不再占首格。
